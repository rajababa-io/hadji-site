Connect Hadji to a private database.

Your database only lets approved addresses in — and Hadji has no fixed address. A Cloudflare Tunnel fixes that: your database opens no port and allows no list of addresses. Three short parts, one for each person involved.
1 · database ownerOpen a tunnelYour side. Outbound only.
2 · Hadji adminAllow the host, save the keyYour Hadji settings.
3 · in a chatConnectOne command.

Whoever runs the database does this once. You need a Cloudflare account with a domain on it, and a machine that can reach the database (inside its network).

  1. Create a tunnel and start its connector In the Cloudflare dashboard, go to Networking → Tunnels → Create a tunnel. Copy the install command it shows and run it on that machine. The connector (cloudflared) only dials out to Cloudflare, so the database opens no inbound port. It needs outbound access to Cloudflare on port 7844.
  2. Publish the database as a TCP hostname On the tunnel's Routes tab choose Add route → Published application. Pick a subdomain and domain (for example db.example.com). For Service URL enter the database's private address with the tcp:// prefix. 
    tcp://10.0.1.25:1433
  3. Lock the hostname with a service token Go to Zero Trust → Access controls → Service credentials → Service Tokens → Create Service Token. Name it, pick a duration, select Generate token, and copy the Client Secret now — Cloudflare shows it once. Then add an Access application for the same hostname with a policy whose action is Service Auth that includes this token. Without a valid token, nobody gets through.
  4. Use a read-only copy Point the tunnel at a read-only replica if you have one, and create a read-only database user for Hadji.
Send Hadji admins: the hostname, the token's Client ID and Client Secret, and the database user's login. Send them through a secure channel, never by chat or email.

A Hadji admin does this once for the organization.

  1. Allow the hostname In Hadji's organization settings, add the tunnel hostname (for example db.example.com) to the hosts chats may reach. The tunnel runs over HTTPS on port 443, so the plain host name is enough.
  2. Save the credentials as a secret Create a secret in Hadji holding the token and the database login. Use these exact names for the token — cloudflared reads them by itself: 
    TUNNEL_SERVICE_TOKEN_ID      # the token's Client ID
TUNNEL_SERVICE_TOKEN_SECRET  # the token's Client Secret
    Add the database user's name and password under whatever names your tools expect.

Chats in your organization can now reach the database. Tell Hadji to connect, or run this in the chat's terminal:

  1. Open the connection 
    cloudflared access tcp --hostname db.example.com --url localhost:1433 &
    The database now answers at localhost:1433 inside the chat, for any database tool. The number after localhost: is only the local side — pick the port your tool expects.
  2. Connect as usual Point your client at localhost and that port, with the read-only user.
Nothing happens, or you get a login prompt? The secret from part 2 isn't reaching the chat, or the Access policy's action isn't Service Auth. A normal Allow policy asks for a browser sign-in, which a chat can't give.

Why this is safe

  • No open port. The connector only makes outbound connections.
  • No address list to keep. Access checks the token, not where the request comes from.
  • Easy to cut off. Disable or delete the service token in Cloudflare and access stops at once.
  • Small blast radius. A read-only user on a read-only replica can't change anything.
